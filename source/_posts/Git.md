 # Git 深度使用指南：从数据模型到工程实践
 
 ## 前言
 
 大多数开发者使用 Git 的方式停留在记忆命令的阶段：`add`、`commit`、`push`、`pull`，按固定顺序执行。当冲突出现或历史需要改写时，往往靠搜索引擎和 Stack Overflow 临时救急。这种工作方式并非不行，但它把 Git 当成一个黑盒，而非一种可推理的工具。
 
 这篇文章不打算罗列命令，也不会从 `git init` 讲起。我们从一个更根本的问题开始：Git 到底在存什么？理解它的数据模型之后，分支、合并、变基、冲突解决都会退化为这个模型上的推论，而非需要死记硬背的操作。
 
 ## Git 的数据模型
 
 ### 对象数据库
 
 Git 的核心是一个内容寻址（content-addressable）的文件系统。所有东西——文件内容、目录结构、提交记录——都存储为不可变的对象，以 SHA-1 哈希为键。对象分为四种类型：
 
 - **blob**：文件的完整内容，不含文件名和路径。同一个文件内容无论出现在多少个提交中，在 .git 里只存一份。
 - **tree**：目录的快照，记录文件名、文件模式（权限）、以及指向 blob 或子 tree 的哈希引用。
 - **commit**：一个提交元对象，包含指向 tree 的哈希、父提交哈希（可能多个）、作者/提交者信息、时间戳和提交信息。
 - **tag**：带注释的标签，指向某个 commit 并附加签名信息。
 
 可以用底层命令直接观察这些对象：
 
 ```bash
 git cat-file -p HEAD          # 查看当前提交的内容
 git cat-file -p HEAD^{tree}   # 查看当前提交对应的 tree
 git ls-tree HEAD              # 列出 tree 的内容
 ```
 
 这意味着什么？每次 `git commit` 不是保存"改了哪些行"，而是创建了一棵新的 tree 对象——一个完整文件系统的快照。Git 在这个快照和上一个快照之间计算差异（diff），但存储的是快照本身。这个设计选择带来了几个关键特性：切换分支不需要重放变更记录，任何历史版本都可以在 O(1) 时间内检出，以及`git log -- <path>`可以在不扫描变更历史的情况下快速定位某个文件的所有关联提交。
 
 ### 引用与可达性
 
 如果对象是 Git 的"数据"，那么引用（refs）就是它的"索引"。分支名（`refs/heads/*`）、标签（`refs/tags/*`）、`HEAD`、`ORIG_HEAD`——这些都是指向某个 commit 哈希的指针，存储在 `.git/refs` 下。
 
 一个提交只要能从某个引用出发，沿着父提交链被遍历到，它就是"可达的"。一旦没有任何引用能到达某个提交，它就是悬空对象，GC 将在一定时间后回收它。这解释了为什么 `git reset --hard` 看起来"不可逆"：`reset` 只是移动了引用，被甩开的提交仍然在对象库里，只是不再可达。如果还记得那个提交的哈希，或者用 `git reflog` 找到它，它完全可以被救回来。真正不可逆的是 GC 之后的物理删除。
 
 ## 暂存区：一个被低估的设计
 
 很多版本控制系统跳过了暂存区的概念，工作目录的修改直接进入提交。Git 的 staging area（也称为 index）在它们之间划了一道人为的界限。这层抽象的价值在日常开发中常常被忽视。
 
 暂存区允许你从一摊修改中**精确挑选**哪些变更进入下一次提交——不是按文件，而是按代码块。这意味着你可以把一个文件里的三处修改拆成两个独立的提交，每个提交都有清晰的语义：
 
 ```bash
 git add -p                    # 交互式挑选代码块
 git add -e <file>             # 手动编辑 diff，只暂存你选中的行
 git reset -p <file>           # 反向操作：从暂存区中移除特定块
 ```
 
 更进一步，暂存区也是解决合并冲突时的"工作台"。冲突标记（`<<<<<<<`、`=======`、`>>>>>>>`）出现在工作目录，而你通过 `git add` 一个已解决的文件，实际上是在告诉 Git："我把这个文件的新版本放进了暂存区，用它来替换冲突版本。"此时文件的三个版本——`O`（共同祖先）、`A`（当前分支）、`B`（合并分支）——都能通过以下命令查看：
 
 ```bash
 git show :1:<file>   # 共同祖先版本
 git show :2:<file>   # 当前分支版本（ours）
 git show :3:<file>   # 合并分支版本（theirs）
 ```
 
 理解这些 stage number 的存在，冲突解决就从"编辑到不报错"变成了"在三个版本之间做有意识的取舍"。
 
 ## 历史改写：rebase 的机制与边界
 
 ### rebase 到底做了什么
 
 很多人把 `git rebase` 理解为"把分支接到另一个分支上"，这样概括会掩盖它在对象层面的真实行为。rebase 的实际操作是：
 
 1. 找到当前分支和目标分支的共同祖先；
 2. 把从共同祖先到当前分支的所有提交，**逐个** cherry-pick 到目标分支的顶端；
 3. 把当前分支的引用移动到新生成的提交链上。
 
 注意第二步的"逐个 cherry-pick"——这意味着 rebase 会为每一个原始提交创建一个**全新的 commit 对象**。新的提交有不同的哈希、不同的 parent 指针，甚至可能因为冲突解决而有不同的 tree 内容。它们和原始提交唯一的共同点是作者信息和提交信息。
 
 这就自然得出了 rebase 的铁律：**不要对已推送到共享仓库的分支执行 rebase**。当你的同事在旧的提交链上做了额外的工作，而你强制推送了一条新的提交链，最终的结果是两条分叉的历史和丢失的协作提交。"不要 rebase 公共分支"不是风格偏好，而是分布式版本控制的客观约束。
 
 ### 交互式 rebase：历史的雕刻刀
 
 如果说普通 rebase 是在搬运历史，交互式 rebase 允许你**重写**历史：
 
 ```bash
 git rebase -i HEAD~5
 ```
 
 它会打开编辑器，展示最近 5 个提交，每行一个 `pick` 指令。你可以：
 
 - `reword`：修改提交信息而不改变内容；
 - `squash` / `fixup`：将多个提交压缩为一个，前者保留提交信息，后者丢弃；
 - `edit`：暂停 rebase，让你修改该提交的内容后再继续；
 - `drop`：直接删除一个提交；
 - `reorder`：交换提交的顺序（通过交换行的顺序实现）。
 
 一个常见的实践是在 feature 分支合并之前执行一次交互式 rebase，将开发过程中零散的"WIP""fix typo""try again"提交整理成一组语义清晰的提交。这不仅让 review 更容易，也让未来的 `git bisect` 能在有意义的粒度上定位问题。
 
 ## merge 的两种策略及其后果
 
 当 `git merge` 合并两个分支时，实际的策略取决于两个分支的关系：
 
 **Fast-forward merge**：如果目标分支可以直接通过移动指针到达当前分支（即当前分支是目标分支的直接后代），Git 默认只移动指针，不创建合并提交。这形成了完全线性的历史，但丧失了"这些提交曾经是特性分支上独立的工作"这一信息。
 
 **Three-way merge**：如果两个分支产生了分叉，Git 会找到它们的共同祖先，计算出三个版本之间的差异，并自动合并。如果同一处代码在两个分支上被不同地修改，产生冲突，则交由开发者解决。此时会创建一个有两个 parent 的合并提交。
 
 关于 `--no-ff`（禁用 fast-forward）：很多人把这个选项当成习惯性用法——"合并时总是加 `--no-ff` 以保留分支信息"。但保留分支拓扑的价值取决于具体场景。对于生命周期很长、涉及多人协作的特性分支，合并提交确实提供了有价值的上下文；对于个人短暂的分支，强制保留合并提交只是在历史里增加噪音。没有普适的最佳实践，只有适合你的团队和项目的取舍。
 
 ## reset 的三个层次
 
 `git reset` 是最常被误用的命令之一，原因是它同时操作三个不同的东西，而 `--soft` / `--mixed` / `--hard` 决定了操作到哪一层为止：
 
 | 模式 | HEAD | 暂存区 | 工作目录 |
 |------|------|--------|----------|
 | `--soft` | 移动 | 不变 | 不变 |
 | `--mixed`（默认） | 移动 | 重置 | 不变 |
 | `--hard` | 移动 | 重置 | 重置 |
 
 这意味着 `git reset --soft HEAD~1` 会撤销上一次 `git commit`，但把所有改动留在暂存区——你可以直接修改后重新提交。而 `git reset HEAD <file>` 本质上等价于新版命令 `git restore --staged <file>`：后者在语义上更清晰，因为它明确表示"把暂存区的文件恢复到和 HEAD 一致"。
 
 反过来，`git revert` 是纯粹的安全网：它通过创建一个**新提交**来撤销某个旧提交的变更，不修改任何历史。在生产分支上，这几乎总是正确的选择。
 
 ## 冲突解决：不止于抹掉标记
 
 冲突标记本身只是 Git 提供的文本级提示。真正有效的冲突解决需要理解冲突的**语义**：为什么两边的修改会在同一行相遇？谁的逻辑更正确？还是说两边都不对，需要第三种方案？
 
 一些被低估的工具：
 
 ```bash
 git checkout --conflict=diff3 <file>   # 显示共同祖先版本，而不只是两边的差异
 git diff --ours / --theirs             # 分别对比两边相对于祖先的变化
 git log --merge                        # 只显示与当前冲突有关的提交
 git merge-file                         # 用自定义的算法参数重新合并单个文件
 ```
 
 `conflict=diff3` 尤其值得设为默认——它会在冲突标记中额外显示共同祖先的版本（`|||||||` 段），让你看到"原始代码是什么样的"，而不只是"两边各自改成了什么样"。这个上下文在复杂的冲突中至关重要。
 
 ```bash
 git config --global merge.conflictStyle diff3
 ```
 
 ## 二分定位：git bisect 的自动化
 
 当回归 bug 出现而你不知道是哪个提交引入的，`git bisect` 用二分查找在提交历史中定位它。手动模式已经很实用，但自动化才是它真正的力量：
 
 ```bash
 git bisect start
 git bisect bad HEAD            # 当前版本有问题
 git bisect good v2.3.0         # 这个版本没问题
 git bisect run npm test        # 每个中间版本自动执行测试
 ```
 
 Git 会自动在好和坏的提交之间二分，对每个中间点运行你指定的脚本，并最终告诉你第一个引入问题的提交。脚本返回 0 表示"好的"，1-127（除 125 外）表示"坏的"，125 表示"跳过"（该提交无法被测试，例如构建失败）。
 
 ## 日志查询：git log 是一门查询语言
 
 大多数人对 `git log` 的使用停留在 `git log --oneline --graph`，但它实际上是一个功能强大的查询引擎：
 
 ```bash
 # 查看某个函数的历史——不仅看它的变更，还追踪其跨文件移动
 git log -L :function_name:path/to/file
 
 # 查看某个文件变更中涉及特定字符串的提交
 git log -S "some_string" -- path/
 
 # 查看某个文件变更中匹配正则的提交
 git log -G "regex_pattern" -- path/
 
 # 查看某个作者在特定时间范围内的提交
 git log --author="name" --since="2024-01-01" --until="2024-03-01"
 
 # 按文件变更量排序（找出改动最大的提交）
 git log --numstat --pretty=format:"%h %s"
 ```
 
 `-S`（pickaxe）和 `-G` 的区别值得注意：`-S` 只在字符串出现**次数变化**时匹配，`-G` 只要 diff 中出现匹配行就匹配。排查"这个变量是什么时候被改成空字符串的"用 `-S`；排查"什么时候有人写了这行可能导致问题的代码"用 `-G`。
 
 ## 工作树：并行开发
 
 当你正在一个分支上做复杂的修改，突然需要切出去修一个紧急 bug，通常的做法是 `git stash` + 切换分支 + 修复 + 切回来 + `git stash pop`。但 `git worktree` 提供了更优雅的方案——在同个仓库中创建第二个工作目录，链接到不同的分支：
 
 ```bash
 git worktree add ../project-hotfix hotfix/urgent
 ```
 
 这样你可以在原目录继续开发，同时在新目录里做 hotfix，互不干扰，也不需要 stash 操作。这在 monorepo 或多任务并行场景中极其实用。
 
 ## 提交信息：写给未来的自己
 
 好的提交信息不是对 diff 的文本描述（"修改了 foo 函数"），而是解释**为什么**做这个变更，以及它的上下文约束。一个在实践中被广泛采用的格式是 Conventional Commits：
 
 ```text
 fix(auth): prevent token refresh race condition
 
 When two concurrent requests both triggered a token refresh,
 the second refresh would invalidate the token set by the first,
 causing a 401 loop. The fix adds a mutex around the refresh path
 and deduplicates in-flight requests.
 
 Closes #3421
 ```
 
 这个提交信息让一年后的维护者（可能就是你自己）不需要重新推理当时的代码上下文，就能理解变更的动机和影响范围。类型前缀（`feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`chore`）不是形式主义——它们是机器可读的元数据，被自动化工具用于生成 changelog 和决定版本号。
 
 ## 清理历史：push --force 的正确用法
 
 `git push --force` 名声不好，但它并非总是危险的。问题在于 `--force` 是无条件覆盖远程引用，而 `--force-with-lease` 是**有条件的强制推送**：只有当远程引用的值和你的本地追踪引用一致时，才允许覆盖。
 
 ```bash
 git push --force-with-lease origin feature/my-branch
 ```
 
 如果在此期间有其他人向这个分支推送了新的提交，`--force-with-lease` 会拒绝推送并报错，让你先 `fetch` 再处理。在个人 feature 分支上执行 rebase 后推送，这应该成为肌肉记忆。
 
 ## 结语
 
 Git 的设计哲学浓缩在它的数据模型里：一切都是不可变的对象，引用只是指针，历史是一个有向无环图。一旦你把这些概念内化——commit 是不可变的快照，branch 是移动的标签，rebase 是重新生成对象——所有命令都变得可推理。
 
 下一次遇到一个不熟悉的 Git 命令，与其去记它的参数，不如问自己：这个操作在对象图和引用系统里做了什么？答案几乎总是在那里。
